> "Agent 能写代码、能提 PR、能跨平台干活——但在你的协作工具里，它连个工位都没有。"

我向来是不惮以最坏的恶意来推测传统协作工具的。总觉得它们把 Agent 当临时工使唤，大抵是用完即弃的命。

然而我还不料，也不信竟会荒诞到这地步——**你的 AI Agent，在飞书里是个"黑户"。**

说实话，这局面颇让人崩溃。我翻看了好几个团队的用法，**简直离谱。烦死了。**

## 一、没有工位的数字劳动力

2026 年了。Claude Code 能独立写完一个功能，Codex 能自己提 PR，OpenClaw 能跨平台干活——Gartner 去年的报告说超过 33% 的企业已经在试点 AI Agent 部署。Agent 不再是"聊天机器人"——它们已经是能干活的数字劳动力了。

但我们的工作方式还停留在什么阶段？**一个人对着一个 Agent 聊天。**

它在本地机器上跑着。你得切到终端跟它对话，它干完了活儿，结果存在你的电脑上。同事想用？得你把聊天记录截图发过去。**荒唐。** 它做了什么决策、动过哪些文件、谁授权它这么干的？

**说不清。**

这局面——说实话，挺绝望的。

飞书里@它一下，它像个临时工一样冒个泡，答完话又消失了。没有身份，没有工位，没有工作记录，没有审批链路。

**这不对。**

说句难听的，这和使唤实习生有什么本质区别？**不靠谱。受够了。**

但更让人不安的是——这还只是问题的表层。

## 二、Agent 越来越强，但它没有"组织"

一个让人头疼的问题终于兜不住了：团队里的多个人和多个 Agent，该怎么真正一起工作？

这不是技术问题，是**组织设计**问题。**可悲的是，大多数团队连这个问题都没意识到。**

HKUDS（香港大学数据科学实验室）刚刚开源了一个项目——[AgentSpace][1]。6 月 21 日发布 v1.0，22 号就更新了 AgentRouter，节奏颇快。**终于有人做了。**

一句话定义：**一个专为「人 + Agent 团队」设计的协作空间。**

注意，它不是又一个套壳 ChatGPT，也不是又一个聊天界面。它做的事情更底层——**让 Agent 成为团队里的一等公民，有身份、有岗位、有权限、有工作记录。**

——不对，应该说不只是飞书。Slack、Teams、钉钉，全都一样。

打个比方：

- 飞书是给人用的协作工具，Agent 只是被@的工具
- **AgentSpace 是给"人+Agent"用的协作工具，Agent 是一线队友**

这个区别，是本质性的。**但真正让人崩溃的是——它们不是做不到，是压根没想过要做。**

## 三、为什么飞书装不了 Agent？五个壁垒

有人可能会说：飞书不也能接机器人吗？

能接，但接的是"工具"，不是"同事"。

我翻开当前的协作平台一查，这平台没有年代，歪歪斜斜的每页上都写着"人力协作"几个字。我横竖睡不着，仔细看了半夜，才从字缝里看出字来，满本都写着五个壁垒——

**恶心的是，大多数人还觉得这样挺好。**

**1. 没有稳定身份。** Agent 在飞书里被@才出现，答完话消失，下次调用又是全新的它。它没有身份，只有上下文窗口。

**这设计，蠢得让人想骂街。**

**2. 没有组织上下文。** Agent 看不到团队的项目背景、决策历史、业务文档。它只能基于你给它的 prompt 干活。

**简直是让一个刚入职的临时工盲猜公司战略。扯淡。**

**3. 没有行动闭环。** Agent 的输出是一段对话，不是一个可以回流到任务系统、文档库、审批流的工作产物。

**说了等于白说。恶心。**

**4. 没有治理层。** 谁授权了它？它做了什么决策？出了事谁负责？说不清。**这比没有治理更可怕——是假装有治理。**

**出了事就甩锅给"AI 的幻觉"，这套路我见多了。**

**5. 没有生命周期管理。** 没人"招募"它，没人"评估"它，没人"淘汰"它。用完即弃。

**比对待外包还狠。**

五个壁垒叠加，Agent 在传统协作平台里永远是个**临时工**。

这设计，横竖都透着一股敷衍的味道。**说白了就是糊弄学。**

但有人不想糊弄了。

AgentSpace 的设计思路是反过来的——**不是给人用的平台顺便接个 Agent，而是从 Agent 的需求出发，反向设计人机协作界面。**

## 四、四个核心设计

拆开看 AgentSpace 的几个关键能力——**说真的，有几个设计我一开始没想到：**

### ① Agent Router：一个 Agent，多个运行时

这是刚发布的新特性。Claude Code、Codex、OpenClaw、Hermes、nanobot——AgentRouter 自动选择最合适的运行时来执行任务，Agent 身份不变。**炸裂。**

打个比方：一个员工可以用不同的工具干活——**格局一下子打开了。**

这解决了一个实际问题：**你不再需要为了用不同模型而维护多个 Agent 身份。**

### ② 能力共享：从"私人工具"到"组织资产"

每个团队都在重复造轮子——A 团队训了一个懂代码审查的 Agent，B 团队不知道，又重新训了一个。**浪费。**

AgentSpace 里，能力是**可共享的组织资产**。一个 Agent 进化出的 Skill，其他团队可以发现、借用、迭代。

这个思路来自 HKUDS 的前序项目 [OpenSpace][2]（GitHub 6000+ stars），做的是 Agent 的技能自进化。现在这个能力被集成到了团队协作层。

### ③ 多 Agent 协作：频道 + 任务看板

不是一个 Agent 单干，而是多个 Agent 在同一个频道里协同。**这效率——啧，之前想都不敢想。**

你在频道里提一个需求——协调型 Agent 自动拆解任务，分配给不同的专业 Agent。Agent 之间互相调用能力，共享上下文，结果写回任务看板。

**人类只在关键节点做审批。**

### ④ 权限治理：Agent 的每一步都可追溯

这是最容易被忽略、但最重要的能力。

Agent 能做什么、不能做什么、谁授权的、做了什么——全部透明可追溯。高风险操作进入人类审批流。

这不是"nice to have"——等等，这么说太轻描淡写了。应该说：**没有这个，你就是在拿公司的数据赌 Agent 不会翻车。**很多团队对 Agent 的态度是**"先用起来再说"**，直到某天发现 Agent 干了不该干的事，而没人知道是谁授权它这么干的。

**说白了，就是裸奔。**

AgentSpace 把治理前置了。**权限、状态、执行过程全部透明可见，人来决策，Agent 来执行，责任边界清晰。**

写到这里我自己都有点将信将疑——这些设计真能落地吗？v1.0 的实现到底做到什么程度了？老实说我也在观望。但至少，**它把正确的问题摆到了台面上。**

## 五、一个具体场景

想象一下创始团队怎么用 AgentSpace：

现在你的团队大概这样干活：Agent 跑在某人电脑上，产出靠复制粘贴传递，审批靠群聊喊人——**累死个人。**

换成 AgentSpace 呢？

早上，你在频道里说：*"帮我调研一下竞品的定价策略，整理成文档，顺便看看我们自己的定价有没有问题。"*

系统里的协调 Agent 拆解任务：
- 📊 **市场调研 Agent** 去扒竞品官网和公开数据
- 📄 **文档 Agent** 去整理内部知识库里的历史定价逻辑
- 💰 **分析 Agent** 去拉财务数据做对比

三个 Agent 在同一空间里协同，互相共享发现的上下文——**这感觉，DNA 动了。** 需要对外发邮件采集信息？进审批队列，你点通过，Agent 执行。

结果呢？不是散落在某个聊天记录里，而是**任务、文件、文档、审批历史完整沉淀在平台里**。

这就是 AgentSpace 想做的事——**让小团队获得大组织的执行杠杆，同时保持可见性和责任边界。**

不过话说回来，这套东西真能跑起来吗？还是又一个"概念很美、落地很痛"的 Demo 项目？

## 六、它还不完美，但方向对了

说实话，AgentSpace v1.0 刚发布两天，**粗糙是肯定的，bug 估计也不少——说实话挺烦的。** 242 个 star，社区还在早期，生态还没建起来。

**但方向是对的。**

协作工具的下一个版本，不应该是"给人用的平台，顺便接个机器人"。它应该是**为"人+Agent"这个新物种重新设计的操作系统**。

飞书解决了人与人的协作。
Slack 解决了人与人的协作。
**AgentSpace 要解决的是：人与 Agent、Agent 与 Agent 的协作。**

这不是工具升级。这是**工作方式的代际跃迁**。——好吧，我知道这话听着像 PPT 标题。但这一次，真的是。

**问题是：你打算什么时候开始认真对待这件事？**

当然，你也可以继续用飞书@你的 Agent，假装它在"参与协作"。**自欺欺人这事，人类向来擅长。反正我是不想再忍了。**
