# Claude Code 说自己能"自愈"了——我跑了一个周末，发现比我想的靠谱

> "好的工具不是替你做决定——而是帮你省掉那些不需要做决定的时间。"

周中 Claude Code 推送了一个新功能：**自愈**。
36 氪热榜上说这是"一锤砸碎开发者 6 大噩梦"。

我向来是不惮以最坏的恶意来推测 AI 新功能的。

毕竟听过太多"颠覆""革命""重新定义"——最后落地一看，不过是把报错信息从红色改成了黄色。

但这个功能，我认真跑了一个周末。

结论先放前面：**确实有用，但有边界。知道边界在哪，比知道功能本身更重要。**

---

## 一、"自愈"到底做了什么

简单说：Claude Code 写完代码后，如果运行时报错，它能自动检测、自动修复。

不需要你手动 debug，不需要你 copy-paste 错误信息。它自己来。

我测了三个典型场景。

**场景一：拼写和语法错误。**

故意在代码里写了 5 个 typo，跑了 3 个项目。5 个全修，0 次误判。这种级别的错误，自愈基本是秒修。

**场景二：import 缺失和依赖冲突。**

故意删掉两个 import，引入一个版本冲突的包。它自动补上了 import，把依赖版本锁了回去。快、准、不啰嗦。

**场景三：逻辑漏洞。**

这个复杂一些。我写了一个函数，参数校验里漏了一个空值判断。正常输入都能跑，但传入 null 会炸。

Claude Code 帮我加了空值判断。

但——它加的是一个通用的 null check，没有考虑我业务场景下的特殊处理逻辑。

**能用，但不是最优解。**

这让我开始理解"自愈"的真正边界在哪了。

---

## 二、自愈的边界：它修得了代码，修不了意图

跑完三轮测试，我对"自愈"的认知是这样的：

**它擅长的：**

- 语法错误、拼写错误、格式化问题
- 明显的依赖冲突和 import 缺失
- 一眼能看出来的 null/undefined 风险

**它不擅长的：**

- 业务逻辑是否正确
- 特定场景下的边界条件处理
- 性能和算法优化

说白了——它修的是**代码层面的 bug**，不是**逻辑层面的 bug**。

代码层面的 bug 是"你写错了"。

逻辑层面的 bug 是"你想错了"。

前者它能搞定。后者不行。

这不是因为 Claude 不够强。是因为它不知道你在想什么。它能看到的只有代码本身，看不到你的业务上下文、你的用户场景、你的架构决策。

这些信息在你脑子里。AI 拿不到。

---

## 三、自愈真正值钱的地方：不是修 bug，是省注意力

说实话，我用了一个周末之后发现——

自愈功能最值钱的，不是它能修多少个 bug。

是它把你的注意力从"低级错误"里解放出来了。

以前我写代码的流程是：写 → 跑 → 报错 → 看报错 → 发现是 typo → 翻白眼 → 修 typo → 再跑。

这几步里，真正需要我脑子的只有"看报错"和"修 typo"。

但"翻白眼"这一步，消耗的情绪能量最大。

一天翻 10 次白眼，下班回家脑子里全是白眼。

现在 Claude Code 把它接过去了。

你写你的逻辑，它帮你擦屁股。

这听起来不像一个"颠覆性"功能——但它确实让写代码这件事变得**更流畅**了。

流畅这件事，写代码的人都知道有多珍贵。

---

## 四、但别急着把脑子也外包出去

自愈好是好。但有一个陷阱，我必须说清楚。

如果你因为有了"自愈"，就不再看它生成的代码了——

**那它不是在帮你修 bug，是在帮你养成坏习惯。**

我说一个自己的操作规范，也建议你考虑：

1. **低风险修改让自愈自动处理**——typo、format、import 缺失，这些不用犹豫，让 AI 自己搞定。
2. **中风险修改看一眼再放行**——null check、类型转换、边界值处理，AI 改完你扫一眼逻辑通不通。
3. **高风险修改必须人工 review**——涉及安全、金额、核心业务逻辑的改动，AI 的建议只是参考，最终决策权留给自己。

这套分层规则的核心逻辑很简单：

**让 AI 做它擅长的（重复检查），把人留给人擅长的（判断和决策）。**

这不是不信任 AI。是正确地信任 AI。

---

## 五、说句实在的

这个周末跑完，我对"自愈"的评价是：

**不是革命性的功能——但它是"让人更愿意写代码"的功能。**

它解决的不是"AI 能不能替代程序员"这种宏大命题。

它解决的是"我今天能不能少翻几个白眼"这种微小而真实的痛苦。

而后者，往往比前者更重要。

如果你已经在用 Claude Code，打开自愈试试。

不是因为它能帮你省多少时间，而是因为它能让你写代码的时候，少一点烦躁，多一点专注。

大抵如此罢。
